# 0076. UUIDv7 for domain entity identifiers

- **Status:** Accepted
- **Date:** 2026-09-28
- **Deciders:** dtbiedrzycki

## Context

Entity identifiers were never given an ADR. `Wishlist`, `Item` and `Hold`
have used UUIDv4 since the domain layer was written, validated by a single
`UuidId` value object, and the question of why — and why not sequential
integers — surfaced during review rather than being settled up front.

Two forces make it worth deciding now. The domain mints its own ids:
`Wishlist.addItem` and `Item.placeHold` construct complete entities, and in
`placeHold`'s case a `Hold` *and* its `ItemHeld` event, before any I/O
happens. That is only possible because ids come from a `TokenGenerator`
port rather than from the database. Separately, the
[performance budget](../spec/performance-and-resource-budget.md) targets
Pi 4-class hardware with a 256MB ceiling and an ~8MB SQLite page cache,
which makes key width a fair question rather than a theoretical one.

## Decision

We will use UUIDv7 for every domain entity identifier — `Wishlist`, `Item`
and `Hold` — generated by the `uuid` package's `v7()`, and validated by
`UuidId` against the v7 version and variant nibbles.

`TokenGenerator.generateSessionId()` stays UUIDv4. A session id is a value
inside a signed cookie, never a database key: it is never indexed, sorted
or joined on, so it gains nothing from v7 and is better left at full
entropy.

We accept that `itemId` and `holdId` carry a readable creation timestamp
to clients, since both appear in `listViewResponseSchema` and
`holdItemResponseSchema`. See Consequences.

## Alternatives considered

- **UUIDv4 (the status quo)** — rejected, though narrowly. It is not wrong;
  v7 is simply strictly better for a value used as a database key, at no
  cost to how the domain mints ids.

- **Sequential integers, composite `(wishlist_id, item_seq)`, assigned by
  the `Wishlist` aggregate** — rejected. It preserves domain-minted
  identity, and measurement confirmed integer keys cut storage by ~80%.
  But at the scale this app targets that is 0.32MB, and a plain
  `INTEGER PRIMARY KEY` — which SQLite aliases to the rowid, building no
  index at all — measured *faster* than the composite at every scale
  (40/55/55µs vs 46/63/65µs for the aggregate-load query at 1k/30k/300k
  items), with comparable storage. So the composite is not the best
  integer scheme even on its own terms, while costing the most: every
  foreign key widens to two columns, `event_log`'s unique key becomes
  `(wishlist_id, item_seq, seq)`, `EventStore.append` and
  `HoldRepository.findByIdempotencyKey` change shape, the wire format has
  to carry a pair, and `item_seq = max + 1` becomes a read-then-write that
  is safe only because SQLite is single-writer inside `UnitOfWork.execute`.

- **Sequential integers, plain `INTEGER PRIMARY KEY`** — rejected. The
  fastest and smallest option measured, but the database assigns the key,
  so `Item.placeHold` could no longer mint a complete `Hold` and its event
  before persisting. That would push insert-then-read-back into the
  application layer and make the domain aware of persistence ordering,
  against ADR-[012](0012-clean-architecture-backend-front-end-does-not-mirror-it.md).
  Read latency is 40–125µs across every scheme and scale tested, against a
  150ms p95 read budget, so this trades an architectural property for
  headroom that is already three orders of magnitude wide.

- **UUID stored as `BLOB(16)` rather than `TEXT(36)`** — rejected as a
  middle path. It keeps identity unchanged and confines the change to the
  Kysely adapters, but measured only a 42% storage saving *and slower*
  reads (99µs vs 74µs at 30k items), because better-sqlite3 allocates a
  Buffer per returned row.

- **ULID, KSUID, Snowflake, TypeID** — rejected. ULID has the same
  intra-millisecond ordering caveat as v7 without being a standard with
  native database types; KSUID is wider; Snowflake needs worker-id
  coordination, which is wrong for a single self-hosted container; their
  shared advantage is compactness, which buys nothing when the value is
  stored as text in SQLite either way.

- **UUIDv47 (store v7, emit a v4-shaped façade by SipHash-masking the
  timestamp)** — rejected. It solves the exposure problem this ADR accepts,
  but it is young, its ecosystem is mostly C and Go, and it would introduce
  a 128-bit key plus rotation storage to a project that has no key
  management for identifiers. This codebase already expresses the same idea
  more simply, with `slug` fronting a never-exposed `wishlistId`; if the
  exposure below stops being acceptable, giving items a public handle is
  the cheaper move.

## Consequences

- Ids sort by creation time, and creation time is recoverable from an id —
  useful when reading logs, where an id is often all there is.

- Inserts land at the right edge of the key's B-tree rather than scattering,
  which is the standard reason to prefer v7 for a database key. At this
  app's scale the effect is not measurable; it is taken as good practice
  rather than as a fix for an observed problem.

- **`itemId` and `holdId` expose their creation time to clients.** A list
  viewer can tell which of two items is older; a holder can read when their
  own hold was placed. This is accepted: ids are not capabilities here —
  `slug`, `ownerToken`, `key` and `holdSecret` are the secrets, and knowing
  an `itemId` grants nothing without them. It does partially soften the
  anti-enumeration stance that collapsed 401 to 404, in that ordering and
  timing become inferable even though ids remain unguessable (74 random
  bits). Revisit by giving items a public handle if that stops being an
  acceptable trade.

- Entropy falls from 122 random bits to 74. Irrelevant for keys, and the
  reason `generateSessionId()` is explicitly excluded above.

- **Monotonicity must come from the library, not a hand-rolled generator.**
  RFC 9562 §6.2 allows filling the bits after the version nibble with
  randomness, which makes ids generated in the same millisecond sort in
  random order — and `CreateList` mints a wishlist id and an item id back
  to back, always within one millisecond. `uuid`'s `v7()` implements the
  monotonic counter method, bumping the timestamp on counter rollover and
  holding order across clock rollback. Node's own `randomUUID()` has no v7
  support and silently ignores a `{ version: 7 }` option, returning a v4:
  any replacement generator must be verified, not assumed.

- `SequentialTokenGenerator`'s id envelope changes shape with `UuidId`, as
  do the UUID literals in tests across the stack. There is no data
  migration, since this lands before first deploy — which is also the
  cheapest moment for it.
